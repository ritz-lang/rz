## R68: where a `let` `@&` borrow error is located (#3924): AT THE `@`

**Measured.** ritz1 reports "cannot borrow `let` binding `x` as mutable" at the
`@` of `@&x`; ritz0 at `x`, two columns on. ritz0's own reference-type check
already lands on the `@` (`test_array_pointee_assign.py`: "`^` marks where the
error lands: on the address assigned", `r = ^@g`).

**Rule.** A diagnostic about an expression is located at the first column of
the smallest expression that is wrong. Here it's the borrow `@&x`, not `x`: the
binding is fine, borrowing it mutably isn't. So it lands on the `@`, for every
`@&` form: expression arms (`Some(v) => pt_x(@&p)`), arguments, tails and
statement-level initialisers (`let q: *C = @&c` reports at the `@`, not at the
`let`). ritz0 moves; ritz1's pinned rows (38:25, 32:10, 55:14) stay, and its
statement-level rows (42:5) move to the `@`.

## R69: the trailing value of a statement body (#3968, #3796): DISCARDED

**Measured.** All three compilers skip the last line of an else-less `if`
statement's body for the whole-array check, and ritz0 and ritz1 accept
`3 => check(3)` with `check` `[[must_use]]` as an arm of a statement `match`.
§17.8 says a call is discarded when it "is an expression statement that is not
its block's value", and R64's §6.6 uses the same words. Neither says when a
block has a value. Corpus: 18 `=> pass` arms already exist; `=> 0` ends 220
lines, most of them in value matches (not split here).

**Rule.** A block has a value only when the block itself is used as one: a fn
body returning a value, a value-returning block's last line, an `if`/`match`
whose value is bound, passed, returned, assigned or tested, or one of these
nested in another. A body that is never a value is the body of a `while`,
`for` or `loop`, a branch of an `if` used as a statement (always so without an
`else`), and an arm of a `match` used as a statement. Its last line is
discarded, like any other statement. So, in such a body:

- a `[[must_use]]` call is "result of [[must_use]] fn 'check' is discarded" (§17.8);
- a whole array is the discarded-array error;
- under R64 (§6.6), a literal or other no-effect expression is "statement has
  no effect". A do-nothing arm is written `_ => pass` (§8.2 already uses it).

One definition, shared by §6.6, §17.8 and the discarded-array check. R64's
tickets (#3491, #3492) adopt it, and their corpus count includes statement-match
arms like `_ => 0`.

## R70: an `f64` into an `f32` slot (#3802): ERROR WITHOUT `as`

**Measured.** §7.5 covers integer narrowing and integer → float only. ritz0 and
ritz1 both accept `let n: f32 = x` with `x: f64`, and `let n: f32 = y * x`
(`y: f32`, which §7.1 widens to `f64`), and `fptrunc` silently. #3607's text
already assumes it's an error.

**Rule.** §7.5, "Float narrowing": an `f64` value into an `f32` slot is an
error, "implicit conversion from `f64` to `f32` can lose precision: write
`<expr> as f32`". The slots are the ones §7.5's integer → float table names:
a `let`/`var` initialiser, an assignment, an argument, a `return`, a field and
an array element. A float literal is exempt (`let f: f32 = 0.1` is the literal
rounded once), and so is a constant expression of float literals (`1.0 / 3.0`),
evaluated as `f64` and rounded once, as §7.5 exempts a constant integer
expression that fits. `f32` into `f64` stays implicit (exact). This is the
R1–R5 principle: a conversion that loses information is written out. The
implementing ticket counts the ritzlib and examples fallout first; every site
is mechanical (`as f32`).

## R71: a pointer value into another pointer type (#3684, #1387): ERROR, EXCEPT THE BYTE POINTER

**Measured.** §3.2 judges `@x` against a `*U`/`@U`/`@&U` slot ("a reference
refers to exactly one type") but says a `*T` *value* "isn't judged". So
`let r: *[3]i32 = q` with `q: *[4]i32` is accepted by both compilers, and
ritz0's `_convert_type` bitcasts any pointer to any other at a call. `*u8` is
the generic byte pointer (alloc, memcpy, mmap, syscalls), and its blast radius
was never measured (#1387).

**Rule.** A pointer or reference value fits a pointer or reference slot only
when the pointees are the same type: `*[4]i32` doesn't fit `*[3]i32`, `*C`
doesn't fit `*D`, `@T` doesn't fit `@U`. **The exception is `*u8`:** a `*T` or
`@T` value fits a `*u8` slot, and a `*u8` value fits any `*T` slot. That's the
byte pointer in both directions, as C's `void*`. `null` fits any pointer.
Anything else needs `as` ("a reference to one type doesn't fit a reference to
another: cast it with `as`", the existing message). `@x` keeps its stricter
rule (§3.2): an address names a typed place, so `@n` of a `u32` still doesn't
fit `*u8` without `as`.

**Measurement gate.** The ritz0 ticket counts the corpus before refusing
anything, split into array-size, element-type, struct and other mismatches.
If more than about 100 sites need an `as`, it stops and comes back to LARB.
#1387's `_convert_type` then bitcasts only what this rule allows.

## R72: struct-to-struct `as` (#3012): REFUSED

**Measured.** §7.5 is silent. By value, ritz0 copies and ritz1 emits IR clang
rejects. Through a reference, ritz0 binds the pointer under the wrong type
("Unknown field 'b' in struct 'C'"), and ritz1 emits invalid IR again. Nothing
in the corpus needs it.

**Rule.** `as` doesn't convert between two different struct types, by value or
through a reference: "cannot cast `C` to `D`: `as` doesn't convert between
structs: build a `D` from the fields". Located at the `as`, the same on all three
compilers. `r as C` with `r` a reference to a `C` stays as #3004 made it (reads
the referent). Reinterpreting memory is a pointer cast, `@c as *D`, which R71
allows with `as`. A layout-checked copy would be a new feature with no user.

## R73: `_` digit separators (#3584): KEEP, AND SPEC THEM

**Measured.** ritz0 accepts `1_000` and `0xFFFF_FFFF`; ritz1's lexer refuses
both with "Parse error". The spec is silent. The corpus has 0 uses outside
tests, so either way costs nothing.

**Rule.** §2.6: "A `_` may separate two digits of a numeric literal, decimal,
hex, binary or octal: `1_000_000`, `0xFFFF_FFFF`. It has no value. It may not
start or end the digits, follow the `0x`/`0b`/`0o` prefix, stand next to
another `_`, or touch a `.`, exponent or type suffix." Kept because long hex
masks are where misread digits cause bugs, and ritz0 already has it. ritz1's
lexer adds it; ritz0 refuses the placements above with a located lexical error.

## R74: `*mut T` in a generic argument (#3959): THE SAME TYPE AS `*T`

**Measured.** A write through a `*T` is already allowed and unchecked (§3.2),
so `*mut` adds nothing. ritz0 treats the two as interchangeable everywhere
except generic identity (`Vec$ptrmut_i32` ≠ `Vec$ptr_i32`); ritz1 parses
`*mut T` as `*T` (#3930). The corpus has 0 `*mut` uses outside
`LANGUAGE_SPEC.md`.

**Rule.** `*mut T` is another spelling of `*T`: the same type, so
`Vec<*mut i32>` is `Vec<*i32>`, one instance with one mangled name. ritz0 drops
`mutable` from type identity and mangling. **For Aaron, not blocking:** with 0
uses and no meaning, the `*mut` spelling could be removed (a migration error,
like `&mut`) so nobody reads `*T` as read-only. Until he says so, it stays as a
spelling.

## R75: a unit enum variant in a constant initialiser (#3673, #3479): ALLOWED

**Rule.** R60's constant-initialiser list gains "a unit enum variant
(`Color.Blue`)". It's a tag known at compile time, like a literal. It may be a
const's whole value, a field of a struct literal, or an element of an array
literal, for `const` and global `var` alike. A payload variant (`Some(3)`) stays
refused for now. #3479 (ritz0) and #3480 (ritz1) take it into the shared
evaluator and the §4.3 text. #3673 lowers it in ritz1's const struct path, with
array fields, after #3479.

## R76: nested variant patterns (#1291): OUT OF SPEC

**Measured.** §8 makes a variant's payload pattern a binding or `_`. ritz0
refuses `Ok(Simple(x))` with a located error (#1321); nothing in the corpus uses
it. Lowering it means a decision tree in the match lowering of both compilers,
which review/5 found are already absorbing rules faster than their structure.

**Rule.** Not a Ritz feature. The located refusal is the rule, on all three:
"a variant's payload pattern is a name or `_`: match the inner value in its own
`match`". Literal payload patterns (`Some(0)`) stay refused under the same
rule. §8.2 says so in one sentence. #1291 closes. If a driver appears, it comes
back as a feature request to Aaron.

## R77: `[[cfg(...)]]` (#1626): NOT ADOPTED

**Measured.** No compiler implements `[[cfg]]`. The spec has only
`[[target_os = "..."]]` (§17.2). `[[cfg]]` is LARB-0013 §3, a draft. Only
test_level42 uses it.

**Rule.** §17.2's `[[target_os]]` is the conditional-compilation attribute.
`[[cfg]]` and `not(...)` aren't adopted. They'd be a second mechanism, and
`not` has no driver. test_level42's target tests are rewritten with
`[[target_os = ...]]`, on fns and, if the compilers support it there, on structs
(if not, the struct case is dropped and a ticket filed). test_cfg_not is
deleted. LARB-0013 §3 is withdrawn.

## R78: the async poll contract (#3728): POLL RETURNS `bool`, THE RESULT LIVES IN THE FUTURE

**Measured.** ritz0's generated `f_poll` returns `i32` with -1 meaning Pending.
That truncates `i64`, pointer and struct results, and a real result of -1 hangs
`await`.

**Rule.** A future's poll returns `bool`: `true` once the body has finished.
On finishing, it writes the result into the future's result field, of the fn's
declared type (none for a unit fn). `await` polls until `true`, then reads the
field. Of the three options, it's the one that suits R79. A `Poll<T>` enum
would give every result type a different poll signature, so an executor
couldn't poll a future without knowing its type. An out-param would need the
executor to supply storage of the right type. A uniform `fn(*u8) -> bool` needs
neither. This is the compilers' internal contract (#3606), so §16 states it
only as far as an executor sees it. Acceptance stays as #3728 wrote it: an
`i64` result above 2^31 and a real -1 both come back intact through `await`, on
ritz0 and ritz1.

## R79: keeping a future and handing it to an executor (#3793): APPROVED BY AARON

**Why it's Aaron's.** It adds a built-in type name and lets `await` take a
held future, not just a call.

**Recommendation.**

1. **The header.** Every generated future begins with a fixed header, whose
   first field is its poll fn, `fn(*u8) -> bool` (R78).
2. **Keeping it.** `var p = f(args)` holds the future, with an inferred type
   that can't be named (#3606).
3. **Handing it over.** A new built-in type `Future`, not generic, means "some
   async fn's future". Any future fits an `@&Future` slot, by reference only; a
   `Future` can't be a value, because its size is unknown. ritzlib's runtime
   takes it: `block_on(rt, @&p)`, `spawn(rt, @&p)`. The runtime polls through a
   built-in, `future_poll(f: @&Future) -> bool`, which calls the header's fn. The
   `poll_fn` argument and the wrappers that named `f_poll` go.
4. **The result.** `await p`, with `p` a held future, drives it to completion if
   it isn't finished and returns its result. After `block_on` it just reads the
   result.
5. **Not covered.** A future stored by value in a struct field or an array,
   which needs a nameable type. A field of type `@&Future` to a future held
   elsewhere works.

The migration for examples 63 and 64 is mechanical: each poll wrapper is
deleted, and each `block_on(rt, @p as *u8, wrapper)` becomes
`block_on(rt, @&p)`. It doesn't wait on #3251, and it's the same on ritz0 and
ritz1.

**Aaron's decision (2026-11-18): "R79: Yes"**, as written. Tickets, all under
#1829:

| #4007 | ritz1: the same, in Sema | #3728, #1816 |
| #4008 | ritzlib `block_on(rt, f: @&Future)`; switches the call lines of its 3 callers | #4006, #4007 |
| #4009 | 63_executor, 64_async_io, test_async_server: delete the poll wrappers | #4008 |

#3606 now depends on #4009 and #4010. `spawn(rt, @&p)` is in #4008 only if the
runtime can take it without a new scheduler (it has no queue of futures
today). Otherwise it's a follow-up.

## R80: runtime polymorphism (#3251): DECIDED BY AARON: NONE

**Aaron's decision (2026-11-18): "No dyn. No runtime polymorphism."** That's
stricter than the recommendation below, which stays only as the record of what
was proposed. Ritz has no runtime-polymorphism feature and no "revisit later"
clause. Static cases use generics with bounds (R55). The §12 fn-pointer-table
idiom is **not** adopted as a spec pattern. A struct of fn pointers, like
spire's app table, is ordinary code and stays as it is; LARB doesn't recommend
it. lexis's sink (#2216's fn-pointer struct) moves onto R55: `trait EventSink`
and `TreeBuilder<S: EventSink>` (#4012, after #3468 and #3469). #3251 is
closed.

*Superseded recommendation:*

**Why it's Aaron's.** The ticket's own "done when" is "confirmed by Aaron".

**Measured.** The drivers are lexis's `handler:& EventHandler` (#2216), tempest
as its implementor, prism's `Backend` (only `MockBackend` today), and spire's
fn-pointer app table (lib/app/mod.ritz:137). R55 gives bounds; R56 removed
closures and sent stateful callbacks here.

**Recommendation: no `dyn` now.**

- **Static cases** (one implementation chosen at compile time, prism's
  `Backend`) use generics with bounds (R55): `fn render<B: Backend>(b: @&B)`.
- **Runtime cases** (mixed collections, callbacks with state: lexis, spire) use
  an explicit table, which spire already does. That's a struct of fn pointers
  taking a `*u8` self, and a `*u8` data pointer:

  ```ritz
  struct Handler
      data: *u8
      on_event: fn(*u8, @Event) -> i32
  ```

  The implementing fn takes `self: *u8` and writes `let s: *Tab = self` (free
  under R71's byte-pointer rule). §12 gets this as the documented idiom, with
  the example.
- **Why:** a `dyn` fat pointer means vtable generation, object-safety rules,
  drops through the object, and borrows of it under R1/R9/R11a, on both
  compilers. Review/5 found both already absorbing rules faster than their
  structure can, and there are four drivers. The explicit table costs each
  driver a few lines and no compiler work.
- **When to revisit:** when there's a fifth driver, or if a driver's table code
  becomes a source of bugs. A later `dyn` would lower to this same table.

*(Superseded: no §12 idiom text is written. lexis is #4012, on bounds.)*

## R81: a free `T` in `impl Box<T>` without `<T>` (#1390): ERROR

**Measured.** The spec writes a generic impl as `impl<T> W<T>` (§5.4, §7.7).
For `impl Box<T>` with no `<T>`, ritz0 dies with a Python traceback ("No method
'get' found for type 'Box$u32'") and ritz1 compiles it (review/5 ritz0.md N4).
The corpus has 0 such impls.

**Rule.** A generic impl declares its parameters: `impl<T> Box<T>`. In
`impl Box<T>`, `T` is an ordinary type name. If no type `T` exists, it's an error
at the `T`: "unknown type `T`: a generic impl declares it, `impl<T> Box<T>`".
The same on both compilers. ritz0's fix belongs to #1390 (its traceback is one
of the ValueErrors); ritz1's is #4002.
