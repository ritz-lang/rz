| | |

## Goal

A wired NIC on real hardware, with harland's network stack (DHCP, ARP,
ICMP, UDP through netd) working over it as it does over virtio-net today.
The epic is done when QEMU CI boots with `-device e1000e`, gets a DHCP
lease, and answers ping and the UDP tools through netd, and Aaron then
confirms the same on the X99 desktop.

Out of scope: Wi-Fi, the X99's second NIC (Qualcomm QCA8171, 1969:10a1),
offloads beyond what is trivial, jumbo frames, VLANs, Wake-on-LAN, and a
second RX or TX queue.

## Shape: a `Nic` library inside netd (D9)

The epic's first draft asked for a CPL-3 driver process beside netd, the
shape `/bin/virtio-net` had. D9 (`RING2_NET.md` "Drivers inside netd (D9)",
`RING1_DRIVER.md` "Decision D9") replaced that shape before any e1000e work
started: a NIC driver is a library behind `trait Nic`, linked into
`/bin/netd`, and netd holds the NIC's `CAP_TYPE_MMIO`, `CAP_TYPE_IRQ`, and
translated DMA domain. #4875 builds this for virtio-net. e1000e is the
second `Nic` implementation:

- `projects/harland/nic/src/e1000e.ritz` implements `Nic`. It makes no
  syscalls, as `RING1_DRIVER.md` PR 8 step 1 requires of the package: netd
  passes in the mapped register window and the DMA runs.
- The kernel probes the NIC, isolates it in its DMA domain, programs its
  interrupt, and grants netd the device. netd and the apps don't change
  apart from netd choosing its `Nic` at boot (below).
- The IOMMU rule is unchanged: a boot with no translated DMA domain spawns
  no netd. Harland has no in-kernel e1000e driver, and this epic adds none,
  so an untranslated e1000e boot has no network. The X99's DMAR (checked
  below) has translation and interrupt remapping, so the desktop does not
  hit this case.

**One netd, chosen at boot.** `RING2_NET.md` "Open questions" leaves "one
netd for every NIC, or one per device" open. This epic takes the smallest
answer that keeps traits static (LANGUAGE_SPEC §12): one `/bin/netd`
binary links both implementations. `DriverBoot` gains a NIC kind, and
netd's entry matches on it once and calls the generic loop `run<N: Nic>`
with a `VirtioNic` or an `E1000eNic`. The loop is compiled once per kind,
with no vtable and no per-frame dispatch. One NIC per boot: the kernel
hands netd the first NIC it finds, in the order virtio-net, then e1000e.

**Registers behind a trait.** The driver reaches its registers through a
small static trait, `trait Regs { fn rd(self: @Self, off: u32) -> u32; fn
wr(self: @&Self, off: u32, v: u32) }`. Its MMIO implementation is a
volatile access to the granted window. Its host-test implementation is a
register model that answers `MDIC` with ready, self-clears `CTRL.RST`, sets
`DD` on descriptors, and so on. Bring-up is a sequence of polled
handshakes, and plain memory can't test one: a `CTRL.RST` poll against a
buffer never clears. The register model is also the only test the I218
paths get before the X99, because QEMU has no model of the PCH LAN.

## What the two parts share

The 82574L and the I218-V are both e1000e-family MACs, and Linux drives
both from `drivers/net/ethernet/intel/e1000e/`: `82571.c` for the 82574L
and `ich8lan.c` for the I218 (`e1000_pch_lpt`). harland uses the part
they share and nothing beyond it:

| Area | Both parts |
|---|---|
| Register window | BAR0, 128 KiB of memory-mapped registers. The offsets below are the same on both |
| Reset | `CTRL` (0x0000) bit 26 `RST`, self-clearing. `CTRL` bit 2 `GIO_MASTER_DISABLE`, then `STATUS` (0x0008) bit 19 `GIO_MASTER_EN` clear: no DMA in flight |
| MAC address | `RAL0`/`RAH0` (0x5400/0x5404), loaded from the NVM by the hardware after reset, `RAH0` bit 31 `AV` set when valid |
| Link | `CTRL.SLU` (bit 6) with autonegotiation; `STATUS` bit 1 `LU`, speed bits 7:6, `FD` bit 0. Link changes raise `ICR.LSC` (bit 2) |
| PHY access | `MDIC` (0x0020): data 15:0, register 20:16, PHY address 25:21, op 27:26 (01 write, 10 read), ready bit 28, error bit 30 |
| RX ring | `RDBAL/RDBAH/RDLEN/RDH/RDT` at 0x2800/04/08/10/18, `RCTL` (0x0100). Legacy 16-byte descriptors: buffer address, length, status (`DD` bit 0, `EOP` bit 1), errors. `RCTL.BSIZE` 00 is 2048-byte buffers, `SECRC` (bit 26) strips the CRC, `BAM` (bit 15) takes broadcasts |
| TX ring | `TDBAL/TDBAH/TDLEN/TDH/TDT` at 0x3800/04/08/10/18, `TCTL` (0x0400), `TIPG` (0x0410). Legacy descriptors with `CMD.EOP`, `IFCS`, `RS`; the device sets `STATUS.DD` on each `RS` descriptor it finishes |
| Interrupts | `ICR` (0x00C0), `IMS` (0x00D0), `IMC` (0x00D8), `ITR` (0x00C4). `RXT0` (bit 7), `TXDW` (bit 0), `LSC` (bit 2) |
| Filters | `MTA` (0x5200, 128 words) cleared; unicast to `RAL0`, broadcast by `BAM`. No promiscuous mode |

Ring lengths are a multiple of 128 bytes (8 descriptors). The virtio
driver's pools are 32 buffers each way; e1000e uses 32-descriptor rings
with one 2 KiB buffer per descriptor, 16 pages per direction.

**Legacy descriptors, no offloads.** Both parts support extended and
packet-split RX descriptors and checksum offload. harland uses legacy
descriptors in both directions and no offload. The stack already computes
its own checksums for virtio-net, and one descriptor format keeps the two
parts on one code path.

**No interrupt coalescing at first.** `ITR`, `RDTR` (0x2820) and `RADV`
(0x282C) are 0, so there is one interrupt per frame, as virtio-net has
today. #4768's latency numbers then compare like with like.
Coalescing belongs to batching (#4876).

### The `Nic` calls on e1000e

| `Nic` call | e1000e |
|---|---|
| `rx_poll` | The descriptor at `rx_next` has `DD` and `EOP` and no errors: `RxFrame` is its buffer, `length` bytes from the Ethernet header (there is no NIC header to strip), `token` the buffer's index. A frame with errors, or without `EOP` (a frame larger than 2 KiB, impossible at MTU 1500 with `LPE` clear), is reposted and skipped |
| `rx_release` | The buffer goes back to the free pool. The refill writes free buffers into the slots at `RDT` and advances `RDT` past them. Tokens are buffer ids, not slot ids, so a release out of order still refills in ring order. This is where e1000e differs from virtio: the device takes RX slots strictly in ring order, not from any available buffer id |
| `tx_buffer` | Reclaim first: every descriptor from `tx_clean` with `DD` set returns its buffer to the pool. `None` when all 32 are in flight |
| `tx_submit` | Write the descriptor at `tx_next`: address, `len`, `CMD = EOP | IFCS | RS`. There is no NIC header, so `TxFrame.bytes` starts at the buffer's first byte. Frames shorter than 60 bytes are sent as they are: `TCTL.PSP` (bit 3) pads them |
| `tx_kick` | One write of `TDT`, once per pass |
| `irq_arm` | Read and acknowledge `ICR`, then write `IMS` with the causes this part uses (below). netd polls RX once more after it, as with virtio |
| `link` | MAC from `RAL0/RAH0`, `STATUS.LU`, MTU 1500, device type `NETDEV_TYPE_E1000E` (3, new in `driver_abi/src/link.ritz` beside `NETDEV_TYPE_VIRTIO`) |

The ownership rule that lets `rx_poll` return the frame in place without a
copy holds on e1000e as it does on virtio. The device writes a descriptor
and its buffer once, between `RDH` and `RDT`, and sets `DD` last. It does
not touch that slot again until software advances `RDT` past it. TX is the
same: a buffer is the device's from the `TDT` write until its descriptor's
`DD`.

## Where the 82574L and the I218-V differ

Facts marked **(dump)** were read from the X99's own config space and ACPI
tables (`docs/hardware/asrock-x99m-extreme4/hwinv/pci.bin`, `acpi/DMAR`)
for this document. The rest come from Linux e1000e (the function names are
given so each can be checked), QEMU's `hw/net/e1000e_core.c`, and the
Intel 82574 and 8 Series/C220 PCH datasheets. Check those against the
datasheet before the code depends on them.

### 1. Interrupts: MSI-X on the 82574L, MSI only on the I218-V

The single largest difference, and one the kernel has to fix, not the
driver.

- **82574L:** MSI-X with 5 vectors, table in BAR3. `IVAR` (0x00E4) routes
  each cause to a vector: RxQ0 bits 3:0, TxQ0 11:8, Other 19:16, each a
  3-bit vector with bit 3 valid (Linux `e1000_configure_msix`). harland
  aims entries 0 (RX), 1 (TX) and 2 (Other: link) at one IDT vector, as the
  virtio probe aims entries 0–2 today, so the IRQ object and `DrvIrqWait`
  are unchanged. In MSI-X mode the causes are `ICR` bits 20 (`RXQ0`), 22
  (`TXQ0`) and 24 (`OTHER`), and `IMS` enables them. BAR3 is the kernel's:
  it is not granted to netd, as virtio's MSI-X table is not.
- **I218-V:** **(dump)** capabilities PM (0xC8), MSI (0xD0) and AF (0xE0),
  and nothing else: no MSI-X and no PCI Express capability. The MSI
  capability reads message control 0x0080: 64-bit address, one message,
  **no per-vector masking**. There is one interrupt for every cause, and
  the causes are the legacy `ICR` bits (`RXT0`, `TXDW`, `LSC`). `ICR`
  reads to clear.
- **The kernel today** has MSI-X only (`drivers/msix.ritz`). The VT-d
  remappable format, `drivers/iommu/dmar.ritz` `msi_addr_remap`, is the
  same address/data pair whether it is written to an MSI-X table entry or
  to the MSI capability. What is missing is MSI itself: find capability
  0x05, write the remapped address and data, set enable, and route through
  an IRTE as `msix_set_entry_to` does. Quiesce has no mask bit to set
  without per-vector masking. It clears MSI enable in config space and
  writes `IMC` = all ones.
- **Testing it before the X99:** QEMU's e1000e also has an MSI capability.
  A kernel that drives QEMU's 82574L through MSI, with its MSI-X table
  left disabled, exercises the I218's interrupt path in CI.

### 2. PHY access and ownership

- **82574L:** the PHY is on the die, at MDIC PHY address 1. QEMU answers
  only address 1 and logs an error for any other. There is no firmware
  agent to arbitrate with. Linux takes `EXTCNF_CTRL.MDIO_SW_OWNERSHIP`
  (0x0F00 bit 5) around PHY access (`e1000_get_hw_semaphore_82574`), and
  QEMU ignores it. Taking it costs nothing and keeps one code path.
- **I218-V:** the MAC is in the PCH and the PHY is a separate chip, the
  I218 itself, joined to it by a PCIe-based interconnect, with SMBus as a
  second, low-power path. The Management Engine shares the PHY, so every
  PHY access, and the MAC reset, is made holding the software flag:
  `EXTCNF_CTRL.SWFLAG` (the same bit 5), set and read back, waiting up to
  1 s while firmware holds it (Linux `e1000_acquire_swflag_ich8lan`). PHY
  registers are paged. The page goes in register 31 (`page << 5`). Pages
  below 768 are at PHY address 2, pages 768 and up at address 1 (Linux
  `e1000_get_phy_addr_for_hv_page`). Bring-up needs only page 0, the
  standard MII registers (BMCR, BMSR, ANAR, 1000BASE-T control).
- **The PHY may not answer at all.** After a power transition, or when the
  ME left the PHY on SMBus, MDIC reads return errors or all ones. Linux
  checks for this (`e1000_phy_is_accessible_pchlan`) and recovers. It
  clears `CTRL_EXT.FORCE_SMBUS` (0x0018 bit 11), then toggles LANPHYPC
  (`CTRL` bits 16 override and 17 value, `e1000_toggle_lanphypc_pch_lpt`),
  then waits for the PHY to come back. It does this in
  `e1000_init_phy_workarounds_pchlan`. This is the most likely place for
  the X99 bring-up to stall.
- **ULP:** Linux's ultra-low-power exit (`e1000_disable_ulp_lpt_lp`)
  returns early for 8086:15a1 (`E1000_DEV_ID_PCH_I218_V2`), so harland
  does not implement it. A PHY that does not answer is the LANPHYPC case
  above.

### 3. Reset

- **82574L:** `GIO_MASTER_DISABLE` and wait for `GIO_MASTER_EN` clear (up
  to 80 ms; Linux `MASTER_DISABLE_TIMEOUT` is 800 × 100 µs), `IMC` all ones,
  `CTRL.RST`, wait for it to clear, `IMC` again, read `ICR` (Linux
  `e1000_reset_hw_82571`). Link and PHY come up with defaults.
- **I218-V:** the same, plus the PCH rules from Linux
  `e1000_reset_hw_ich8lan`:
  - The reset is made holding `SWFLAG`, and the hardware releases it.
  - `CTRL.PHY_RST` (bit 31) goes with `CTRL.RST`, unless `FWSM` (0x5B54)
    bit 6 `RSPCIPHY` is clear. Then the ME blocks a PHY reset (Linux
    `e1000_check_reset_block_ich8lan`), and the MAC is reset alone.
  - Wait 20 ms, then for `STATUS` bit 9 `LAN_INIT_DONE`, and clear it
    (`e1000_lan_init_done_ich8lan`).
  - Then come the post-reset PHY steps (`e1000_post_phy_reset_ich8lan`).
    For an `e1000_pch_lpt` part with default NVM settings these reduce to
    the PHY-accessible check above. They also leave the LCD (PHY)
    configuration that firmware loaded from the NVM in place.
- **Function-level reset:** **(dump)** the I218's AF capability reads
  0x03: transactions pending and FLR are both supported. The kernel's
  quiesce can use AF FLR (bit 0 of AF control) as a reset that does not
  depend on the MAC's own state. The 82574L has no AF capability, and FLR
  through its PCIe capability is optional, so it is not assumed.

### 4. MAC address and the NVM

- **82574L:** the NVM is an EEPROM or flash behind `EERD` (0x0014), and
  the hardware loads words 0–2 into `RAL0/RAH0` after reset. QEMU loads its
  `mac=` there with `AV` set.
- **I218-V:** the GbE NVM is a region of the PCH's shared SPI flash. There
  is no `EERD`. Software reads it through the flash registers in BAR1
  (`GFPREG`, `HSFSTS`, `HSFCTL`, `FADDR`, `FDATA0`). **(dump)** BAR1 is
  4 KiB at 0xfb239000. The hardware still loads the MAC into `RAL0/RAH0`.
- **Plan:** read `RAL0/RAH0` on both, and require `AV`. A NIC whose `AV`
  is clear is refused with a log line naming it. The flash reader goes in
  only if the X99 shows `AV` clear, which would also mean the NVM's other
  words are not loaded. So BAR0 is the only window netd gets on either part.

### 5. Errata and power settings on the PCH

Linux's `e1000_initialize_hw_bits_ich8lan` and `e1000_init_hw_ich8lan`
set fixed errata bits in `CTRL_EXT`, `TXDCTL` (0x3828: `GRAN`,
`WTHRESH` 1), `TARC0/1` and `RFCTL` for every PCH part. The I218 driver
copies them as they are, each with the Linux line it came from. Three
power features stay at their NVM defaults at first and get a switch-off
path only if the X99 shows the symptom:

- **K1**, a power state on the MAC–PHY interconnect (`e1000_configure_k1_ich8lan`).
  The symptoms are dropped frames or link flaps at 1 Gb/s.
- **EEE**, Energy-Efficient Ethernet (`e1000_set_eee_pchlan`). The symptom
  is a long first-frame latency after idle, visible in `net_latency.sh`.
- **The I217/I218 in-band timeout at 10/100**, set on each link change
  (Linux `e1000_check_for_copper_link_ich8lan`, `I217_INBAND_CTRL`). The
  symptom is a link that does not pass traffic at 100 Mb/s.

The 82574L in QEMU has none of these. Its real-silicon errata, such as
ASPM L0s, don't apply in emulation, and harland doesn't target a physical
82574L.

### 6. DMA and the IOMMU on the X99

- **(dump)** The DMAR has two units. 0xfbffd000 covers only the HD audio
  device, 00:1b.0. 0xfbffc000 is `INCLUDE_PCI_ALL` and covers the I218 at
  00:19.0, requester 0x00C8. `dmar.ritz` already finds a device's unit by
  scope or by the catch-all. The X99 is the first boot where the NIC is not
  on the first unit, so the probe's "isolated" log line should name the
  unit.
- **(dump)** The only RMRR (0x7ae64000–0x7ae72fff) is for USB: 00:14.0,
  00:1a.0, 00:1d.0. None is for the NIC, so the NIC's domain starts empty,
  as virtio-net's does.
- **(dump)** The DMAR flags are 0x3: interrupt remapping and
  `X2APIC_OPT_OUT`. This is not a NIC difference, but it is a risk for the
  MSI path above: the IRTE destination format has to match the APIC mode
  the kernel actually runs in on this board.
- **(dump)** The PCI command register reads 0x0002: memory decode on, bus
  master off, as firmware left it. The probe turns bus master on after the
  domain is attached, as `virtio_net_isolate` does.
- QEMU's e1000e issues all its DMA through the emulated IOMMU (`pci_dma_*`).
  It needs no `iommu_platform=on` and has no feature bit to negotiate,
  unlike virtio's bit 33.

### 7. Link bring-up time

- **82574L (QEMU):** autonegotiation completes on a timer about half a
  second after `SLU`, and `LSC` fires.
- **I218-V:** real autonegotiation, usually 2–3 s and up to about 5 s on
  gigabit. netd publishes `NetInfo` with link down at once and again on
  `LSC`, and DHCP starts on link up. It does not wait in bring-up. The
  kernel seat's self-test window (`\harland\net-selftest`) has to allow for
  it on the X99.

### Summary

| | 82574L (QEMU `e1000e`) | I218-V (X99, `e1000_pch_lpt`) |
|---|---|---|
| PCI ID | 8086:10d3 | 8086:15a1, 00:19.0, rev 05 **(dump)** |
| Interrupt | MSI-X, 5 vectors, `IVAR`; harland uses 3 entries on one vector | MSI, 1 message, no masking **(dump)**; legacy `ICR` causes |
| PCI caps | PM, MSI, PCIe, MSI-X | PM, MSI, AF (FLR) only **(dump)** |
| BARs netd gets | BAR0 | BAR0 (BAR1 flash only if `AV` is clear) |

| MAC | `RAL0/RAH0` (`EERD` behind it) | `RAL0/RAH0` (SPI flash via BAR1 behind it, no `EERD`) |
| Errata/power | none in emulation | `initialize_hw_bits` errata; K1, EEE, in-band timeout as fallbacks |
| Link up | about 0.5 s | 2–5 s, real autonegotiation |
| Tested by | QEMU CI | host register model, then the X99 |

## Kernel side

The kernel's NIC code is virtio-specific in three places, and e1000e
generalizes each:

1. **The probe and grant.** `NicGrant`, `virtio_net_ring1_probe` and
   `net_ring1_spawn` find a virtio-net and record virtio's capability
   windows. An e1000e probe matches 8086:10d3 and 8086:15a1. It isolates
   the NIC in its domain and turns bus master on, as
   `virtio_net_isolate` does. It programs MSI-X (82574L) or MSI (I218-V)
   at the BSP, and grants BAR0 as one `CAP_TYPE_MMIO` window. `DriverBoot`
   carries the NIC kind, and its `msix_*` fields name the 82574L's
   entries. They mean nothing on MSI.
2. **Quiesce.** `DrvDevice` records a virtio `status_va`, and
   `quiesce_device` calls `vio_status_reset`. The record gains a kind.
   e1000e's quiesce masks the interrupt (`IMC`, then the MSI-X entries, or
   MSI enable off). It then sets `GIO_MASTER_DISABLE` and waits for
   `GIO_MASTER_EN` clear, sets `CTRL.RST` and waits for it to clear. The
   reset counts as complete only when both waits succeeded. Only then are
   the runs freed rather than quarantined, as virtio's 0 readback works
   today. On the I218 the kernel takes `SWFLAG` first. If a dying netd
   held it, the flag is already software's.
3. **Restart.** `netd_restart` (#4875) refuses a NIC whose quiesce
   quarantined a run. That rule is the same for e1000e, and so is the
   restart budget. A replacement netd resets the device itself, as every
   bring-up does.

## Tests

- **Host:** the `nic` package's e1000e tests run on the register model:
  reset and its timeouts, the MAC from `RAL0/RAH0` and refusal without
  `AV`, an MDIC read, write and error, and RX refill in ring order after an
  out-of-order `rx_release`. They also check that `tx_buffer` returns `None`
  with every buffer in flight and a buffer again after `DD`, and that 300
  sends recycle TX descriptors (the #4073 rule). The I218 set adds the
  `SWFLAG` handshake and its 1 s timeout, PHY paging and addresses, the
  `RSPCIPHY` block, `LAN_INIT_DONE`, and the LANPHYPC recovery when the
  PHY reads all ones.
- **QEMU CI:** `tools/test_msix_boot.sh` gains e1000e boots. On q35 with
  `intel-iommu,intremap=on,eim=on` and `-device e1000e,netdev=net0,romfile=`,
  each boot checks DHCP, ping, the UDP tools, and `\harland\netd-restart`
  with the NIC reset before each restart. One more boot runs the 82574L on
  MSI. `tools/net_latency.sh` takes the NIC as a parameter and adds a dated
  `RING2_NET.md` Rollout entry for e1000e against virtio-net.
- **X99:** Aaron boots the stick: a DHCP lease from the LAN, ping from
  another host, the UDP tools, and `net_latency.sh`'s guest side if the
  host side can reach it. The X99 README's Ethernet row then moves from
  "gap" to the driver.
